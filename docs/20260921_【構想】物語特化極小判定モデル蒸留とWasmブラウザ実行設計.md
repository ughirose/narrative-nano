### 1. モデルアーキテクチャとパラメータ制約の物理的内訳
モデルバイナリを2〜5MBに収める場合、利用可能な総パラメータ数は約200万〜500万パラメータ（2M〜5M params）に厳格に制限されます（INT8量子化時）。
この規模で最も大きなボトルネックとなるのは、「語彙（Embedding）テーブルによるメモリ圧迫」です。通常のLLMのように32,000語〜64,000語の語彙辞書を持たせると、埋め込み層だけで数MBを消費し、計算層（Transformerブロック）に割り当てる容量が枯渇します。
【5MBバイナリの物理的割り当て構成（INT8量子化前提）】 総容量: 5.0 MB (約 5,000,000 bytes)  ├── ① 入力埋め込み層 (Factorized Embedding) : 約 0.8 MB (16%)  ├── ② バックボーン (4層 極小Transformer)   : 約 3.6 MB (72%)  └── ③ マルチタスク判定ヘッド (3系統)       : 約 0.6 MB (12%)

| --- | --- | --- | --- |

### 2. マルチタスク出力ヘッドの設計
小説の「暗黙的型推論」を成立させるため、バックボーンから出力されたトークン表現（192次元）に対して、3つの極小分類ヘッドを並列に接続します。
                         [入力文: 「アレクが」「白銀の指輪を」「手にとった」]                                                │                                                ▼                                    [4層 極小Transformer Encoder]                                                │ (Hidden: 192次元)                        ┌───────────────────────┼───────────────────────┐                        ▼                       ▼                       ▼            【Head 1: 境界抽出】       【Head 2: 役割・格関係】   【Head 3: 状態・様態】            (Token BIO Tagging)        (Case & Syntax Pointer)    (Modality & State)             固有名詞・アイテム境界     主語(GA)、目的語(WO)、    セリフ/地の文/内心独白、             [B-CHAR, I-CHAR, O...]    述語への係り受けタグ      嘘・秘匿トリガーフラグ
- Head 1: エンティティ境界タグ（B-I-O Classification）: 各トークンが「人物名（CHAR）」「アイテム（ITEM）」「場所（LOC）」のどこに属しているかを分類（出力次元: 7値）。
- Head 2: 格関係・役割タグ（Case & Dependency Labeling）: 助詞との接続に基づき、そのエンティティが「動作主（主語: が/は）」「対象（目的語: を/に）」「所有（の）」であるかを確率出力。
- Head 3: 様態・主観認識トリガー（Modality & Epistemic Trigger）: かぎ括弧の内外判定（発話 vs 地の文）と、「秘密に触れている」「不審な行動をとっている」といった主観認識更新のトリガー確率（シグモイド出力）を判定。

### 4. ブラウザ内ランタイム（Wasm SIMD vs WebGPU）の性能検証
ブラウザ環境において「サブミリ秒（< 1ms）」を達成するためのランタイム選定には、計算アーキテクチャ上の重要なトレードオフが存在します。

| 実行ランタイム | 処理エンジン | メリット | ボトルネック・課題 | 適合性判定 |
| --- | --- | --- | --- | --- |
| WebGPU  (GPUシェーダー) | ONNX Runtime Web / WebGPU バインディング | 大量並列演算に強い。大行列積の計算速度は最速。 | カーネルディスパッチのオーバーヘッド（0.2〜0.5ms）が存在。  小さなトークン列（数十文字）ではGPU転送コストが勝る。 | △ バッチ処理には良いが単文即時判定には過剰 |
| WebAssembly SIMD  (CPUマルチ/単一コア) | ONNX Runtime Web / Wasm SIMD (128bit) | CPUローカルで完結し、呼び出しオーバーヘッドが数マイクロ秒。  メモリ帯域・キャッシュヒット率が高い。 | 長文（数千トークン）の一括計算ではGPUに劣る。 | ◎ サブミリ秒の単文タイピング判定に最適 |

#### 推奨される実行構成：Wasm SIMD によるローカル即時評価
モデルサイズが3〜4MB程度、かつ入力長が直近の入力（1文〜数文：約50〜100文字）に限定されている場合、GPUを起動するよりもWasm SIMD（128-bitベクター演算）を用いたCPU直接実行の方が、レイテンシのばらつき（ジッター）が極小化され、実測0.3〜0.8ms程度での推論完了が十分に狙えると考えられます。
### 5. ビジネス価値と知財・参入障壁（Moat）の検証
この極小判定モデルを内製することは、プロダクトの持続可能性および企業価値の防壁において、以下のような非連続なアドバンテージをもたらします。
- 推論インフラ原価（COGS）の完全な物理的遮断:
  - 通常のAIエディタは、ユーザーが文字を打つたびにAPIコスト（月間数百円〜数千円/人）がプラットフォーム側に累積します。
  - 本モデルは初回ロード（数MBの静的配信＝CDN転送費数円）以降、クライアント端末のCPUを直接消費するため、プラットフォーム側の月額運用原価は$0となります。これにより、他社が追随できない無料プランの開放や、85%〜90%以上の高い粗利率が実現します。
- 「オフライン・ゼロレイテンシ」という模倣困難な体験:
  - クラウドAPIに依存する競合製品は、通信環境の悪い場所（移動中の新幹線や機内）では一切の判定が停止します。
  - 完全ローカル完結の極小モデルは、オフラインでもミリ秒単位で「設定破綻の波線」を返し続けるため、プロ作家の過酷な執筆環境において圧倒的な信頼（スイッチングコスト）を形成します。
- データフライホイールによる独自アセット化:
  - 作家が「この警告は演出として承認」「このノードを修正」と判断したインタラクションログ（差分）は、モデルの再学習データセットとして蓄積されます。
  - 汎用LLMでは再現できない「実際の創作現場で発生する破綻パターンと例外（演出）の境界データ」そのものが、他社が容易に買えない知的財産（Data Moat）へと転化します。

### 1. アノテーションスキーマの定義（Studentモデルのヘッドと1:1対応）
Teacher LLMが出力すべきJSONスキーマは、Studentモデルの学習損失（Multi-task Loss）に直接変換可能な構造として定義します。
export interface DistillationSample {  text_snippet: string;           // 入力テキスト（1〜3段落、150〜300文字程度）  entities: EntityAnnotation[];   // Head 1: B-I-O 境界  relations: RelationAnnotation[];// Head 2: 格関係・係り受け  modality: ModalityAnnotation;   // Head 3: 様態・主観認識トリガー}export interface EntityAnnotation {  start_char: number;             // 文字開始位置（0-indexed）  end_char: number;               // 文字終了位置（exclusive）  surface: string;                // 表層文字列（例: "白銀の指輪"）  label: 'CHAR' | 'ITEM' | 'LOC'; // 登場人物、アイテム、場所}export interface RelationAnnotation {  predicate_span: [number, number]; // 述語の文字スパン（例: [20, 23] "手にとった"）  arguments: {    target_span: [number, number];  // 項の文字スパン    case_role: 'GA' | 'WA' | 'WO' | 'NI' | 'DE' | 'FROM' | 'TO'; // 格助詞・意味役割  }[];}export interface ModalityAnnotation {  text_type: 'DIALOGUE' | 'NARRATION' | 'MONOLOGUE'; // セリフ、地の文、独白  speaker_entity_span?: [number, number];             // 発話者・思考者の文字スパン  epistemic_trigger: {    has_trigger: boolean;                             // 主観認識更新の契機となるか    action_type?: 'REVEAL_SECRET' | 'DECEPTION' | 'ACQUIRE_FACT' | 'POSSESSION_CHANGE';    detail?: string;                                  // トリガーの簡易要約  };}

### 3. エッジケースに対するラベリング基準の標準化
小説特有の表現によるデータの揺らぎを抑制するため、以下の境界ガイドラインをプロンプト内、あるいは前処理・後処理フィルターとして定義しておく必要があります。

| エッジケース | 発生しやすい表記 | アノテーション規範（Ground Truth） |
| --- | --- | --- |
| 記号・修辞を含むアイテム名 | 『白銀の指輪』、＜魔導炉＞ | 括弧記号（『』や＜＞）は含めず、内容の文字列のみをスパン指定する。  （例: start: 17, end: 22, surface: "白銀の指輪"） |
| 代名詞・指示語 | 「あいつ」「彼」「その剣」 | 代名詞は原則としてエンティティ抽出の対象外とし、明示的な名詞・固有名詞のみを抽出。文脈照応は上位レイヤーに委ねる。 |
| 複合名詞の分割粒度 | 「帝国近衛騎士団長アレク」 | 称号・役職と名前が結合している場合、[CHAR: アレク] のみを抽出するか、称号を属性として別分離する。Studentの語彙圧迫を防ぐため、固有名称部分のみを切り出す。 |
| 主語の省略（ゼロ代名詞） | （アレクが）「剣を抜いた」 | 省略された主語を無理に推測スパンとして埋め込まず、relations.arguments には「テキスト上に明示的に存在する語」のみをバインドする。 |

### 4. 自動バリデーション（Quality Gate）パイプライン
Teacher LLMによる出力は確率的なため、文字オフセットの計算ミスやJSONの破損が一定割合（数％）で混入します。これをStudentモデルの学習データセット（PyTorch Dataset）に投入する前に、決定論的スクリプトで弾く検証ゲートを設けます。

### 1. Jev / OpenJevの思想を物語IDEへ転用する本質
チェスエンジンやゲームAIにおけるJevやNNUE（効率的更新可能ニューラルネットワーク）、およびそのオープン派生（OpenJev系）の核心は、以下の3原則に集約されます。
- 局面（状態）の疎な特徴量化（Sparse State Representation）: 盤面全体を画像や長大な行列として見るのではなく、「どの駒がどこにあるか」をビットや疎なインデックスの集合として表現する。
- アキュムレータによる差分更新（Incremental Accumulator）: 手が指された際、盤面全体を再計算するのではなく、「動いた駒の差分（引き算と足し算）」だけをアキュムレータ（中間ベクトル）に反映する（計算量は O(1) または O(Δ)）。
- 超極小な評価関数（Tiny Evaluation Network）: アキュムレータから直接、数層の極小MLPや線形重みを通すだけで、その局面の「合法性・評価値（Eval）」をナノ秒〜マイクロ秒単位で出力する。
[従来のステートレスNLP] テキスト入力 ──(毎回ゼロからトークナイズ)──► Transformer (数MB〜数GB) ──► 状態抽出 (重い)[Jev的・物語アキュムレータ方式] テキスト入力 ──► 差分検知 (シャドウアンカー)                        │                        ▼ (引き算と足し算のみ)                  [物語状態アキュムレータ (Accumulator)]                   - キャラの現在地、所持品、認識ベクトル                        │                        ▼ (極小MLP / 内積)                  [合法性・破綻評価スコア (Eval)] < 0.01ms
これを小説執筆に適用すると、「本文のキーストロークは、物語という盤面に対する指し手（Move）である」という見立てが成り立ちます。
### 2. データ構造とモデルの密結合（Co-design）アーキテクチャ
先ほど定義した4つのコアスキーマ（Character, Item, Location, Event）を、Jev的な「疎な特徴空間（Sparse Feature Space）」として直接ベクトル化します。
#### ① 物語盤面（Story Board）のビット/インデックス表現
登場人物・アイテム・場所・事実の全組み合わせを、疎な特徴量（Feature ID）としてマッピングします。
- Feature_1042: Char_Alec が Item_Ring を「所持している」
- Feature_2105: Char_Alec が Fact_RingCurse を「知っている」
- Feature_3088: Char_Alec の現在地が Loc_Checkpoint である
#### ② 差分アキュムレータ（Narrative Accumulator）の挙動
エディタの裏側に、作中時間・エピソードごとの「アキュムレータ（例: 256次元〜512次元の低次元浮動小数点ベクトル）」を常時保持させます。
- 作家が「アレクは指輪を手にとった」と書く。
- シャドウアンカーが反応し、差分トランザクションが発生。
- アキュムレータに対して、対応する特徴ベクトルの足し算・引き算（SIMD命令数回）を実行するだけで、現在の物語世界の論理状態が瞬時に最新化される。
#### ③ 破綻検知（違法手判定）のスコアリング
「この状態で、アレクが『その呪いは本物か？』と発言する」というアクションが発生した際、アキュムレータと発話特徴の内積（または2層程度の極小MLP）を計算します。
- Score < Threshold（非合法手）：アレクの認識ベクトル内に「呪いの知識」が含まれていないため、評価スコアがマイナスに振り切れ、即座に「設定のほころびアラート」が発火する。
### 3. OpenJev派生モデルから着想を得た3つの具体的アプローチ
OpenJevの派生系（Bitboard特化型、埋め込みアキュムレータ型、グラフ埋め込みハイブリッド型）をベースに、小説IDEに最適化可能な3つの構造を比較検討します。

| アプローチ | データ構造の持ち方 | 判定エンジンの仕組み | モデルサイズ | 推論レイテンシ | 実装・運用の適合性 |
| --- | --- | --- | --- | --- | --- |
| 案A: 純粋ビットボード型  （Bitboard / Rule-Accumulator） | 全エンティティと属性をビット配列（BitSet）で表現 | ビット論理演算（AND / XOR / Popcount）による完全決定論的判定 | 数十KB  （重みモデル不要、ルールテーブルのみ） | < 1 μs  （ナノ秒オーダー） | 高。ただし表現が固く、「曖昧なニュアンス」の判定には弱い。 |
| 案B: 疎特徴アキュムレータ型  （Jev-NNUE アダプテーション） | 物語スキーマの特徴IDから低次元埋め込みをアキュムレータに線形加算 | 差分更新されたアキュムレータ ＋ 2層極小MLPによる整合性スコアリング | 500KB 〜 1.5MB | < 0.05 ms  （サブミリ秒を大幅に下回る） | 極めて高い。決定論的制約と自然言語の曖昧性のバランスが最も良い。 |
| 案C: 局所グラフ埋め込み型  （Dynamic Graph-Pointer） | ノード間の隣接状態を有向差分リストで保持 | 局所サブグラフの埋め込み内積（コサイン類似度）による逸脱度検知 | 1MB 〜 3MB | 0.1 〜 0.3 ms | 中。グラフの更新ロジックがやや複雑化するリスクあり。 |

#### 推奨：案B（Jev-NNUE型アキュムレータ）の優位性
案Bを採用した場合、前述の「2〜5MBのTransformer」と比較して以下のような圧倒的な構造的優位が生まれます。
- モデルサイズがさらに1/4〜1/5に圧縮（500KB〜1MB程度）: 重厚なMulti-Head Attention層やLayerNormの多層スタックが不要になり、埋め込み辞書と極小MLPだけで完結するため、スマートフォンのブラウザでも一瞬でロード可能。
- 計算量が文章全体の長さに依存しない: 100万文字の長編であっても、直前のキーストロークによる差分更新（Δ）のみを評価するため、どれだけ物語が長大化してもレスポンス速度が一切劣化しない（O(1) スケーラビリティ）。
### 4. ビジネスと競争優位（Moat）への影響
この「データ構造とJev的評価関数の密結合」というアプローチは、Worldcraftの事業価値と参入障壁を一段上のレベルへ引き上げる可能性を秘めています。
[従来の参入障壁] 一般的なNLPモデル ──► 誰でもHuggingFaceからダウンロードして真似できる（Moatが薄い）[Jev的アプローチによる参入障壁] 「物語の型スキーマ（データ構造）」×「差分アキュムレータ」×「特化評価器」   └─ データ構造とモデルが不可分に結合しているため、      他社がLLMラッパーを作っても物理的に追いつけない速度と原価構造が完成する
- 「真似できない軽快さ」の確立: 他社がクラウドLLMや重いブラウザ内NLPを回して数十ミリ秒〜数秒のレイテンシで苦しんでいる横で、Worldcraftはキータッチの瞬間にマイクロ秒で波線を引くことができます。この「吸い付くような書き味」は、エンジニアリングとしての極めて深い堀になります。

- 作家が文章を書き直した（BackSpaceやアンドゥ、途中の大幅書き換え）際の、アキュムレータの巻き戻し・再同期のロジック。

Response: B案（Jev型アキュムレータ）単体のアプローチは、計算量 O(1) かつマイクロ秒単位の超低遅延で「離脱のない書き味」と「ゼロCOGS（サーバー費用ゼロ）」を実現できる強みがある一方で、「自然言語の文脈・ニュアンス・曖昧性をどこまで扱えるか」という表現力の壁に直面しやすいという懸念は十分に検討に値すると考えられます。
自然言語はチェスのように厳密な「指し手（離散記号）」に還元しきれない領域（比喩、皮肉、主語の省略、暗黙の了解など）を常に孕んでいます。このため、B案単体に閉じるのではなく、オープンウェイト系LLM（Qwen 2.5、Gemma 2、Llama 3系などの軽量モデル）や他の機構と組み合わせたハイブリッド構造を検討することは、ツールの実用性と汎用性を高める上で極めて論理的な方向性であると推測されます。
この観点に基づき、考え得る複数のハイブリッド構成および代替手法について、技術的裏付けと運用面（リソース消費・ROI）から多角的に検証します。
### 1. B案単体の限界と、LLM連携が必要となる境界線
Jev的な決定論的アプローチと、オープンウェイトLLMが得意とする領域には、下表のような明確な機能的分担が存在すると考えられます。

| 領域・タスク | Jev / アキュムレータが得意な領域 | オープンウェイトLLM（1B〜8B）が得意な領域 |
| --- | --- | --- |
| 処理速度 | マイクロ秒（< 0.05ms）：キータッチに完全追従 | 数十〜数百ms（生成なら数秒）：タイピング中に毎回回すのは困難 |
| 得意な判定 | 排他・代数制約（アイテムの所持、位置・速度、生没年、明確な秘密） | 文脈・意味理解（感情の機微、遠回しな告白、騙し合いの空気感） |
| ゼロ代名詞 | 「誰がやったか」が明示されないと判定不能 | 直前までの対話の流れから「発話者・主語」を文脈推論 |
| 例外の解釈 | ルール違反として一律に弾く（誤爆リスク） | 「これは特殊能力や叙述トリックではないか」という意図の汲み取り |
| 修正提案 | 「矛盾しています」という事実の指摘のみ | 「第12話でこういう伏線を足すと自然に繋がります」という代替案提示 |

この非対称性を踏まえると、「決定論的な制約チェックはJevがミリ秒で担い、曖昧な文脈調停や解説生成をオープンウェイトLLMが受け持つ」というハイブリッド設計が最も自然な補完関係を描ける可能性があります。
### 2. 考えられるハイブリッド構成・代替アプローチの比較
Jev的アキュムレータとオープンウェイトLLM、あるいはその他のアーキテクチャを組み合わせた構成として、以下の4つのアプローチが検討対象になり得ます。
【パターン1: 2階層（Tiered）パイプライン】 キーストローク ──► [L1: Jev (即時)] ──(矛盾の疑いのみ)──► [L2: オープンウェイトSLM (非同期)]【パターン2: 投機的実行（Speculative Verification）】 テキスト ──► [Jev (暫定フラグ付け)] ──► [LLM (バックグラウンドで確定・調停)]【パターン3: コンパイラ＋ランタイム分離】 [LLM (文章からJev用トランザクションを生成)] ──► [Jev (超高速な状態更新と検証)]【パターン4: ハイブリッド・リトリーバル（Embedding + Graph + Jev）】 [局所Dense Embedding] ＋ [Jev疎特徴量] ──► 複合類似度・整合性判定

| アーキテクチャ構成 | 仕組み・処理フロー | メリット | デメリット・課題 | 適合性の検証 |
| --- | --- | --- | --- | --- |
| パターン1: 2階層（L1/L2）多重ガード  (Jev即時検知 ＋ SLM非同期調停) | ①タイピング時はJev（L1）がミリ秒で走査。  ②明らかな型破綻、または「判断保留（グレーゾーン）」の箇所のみ、数秒のアイドル時や明示操作でオープンウェイトSLM（L2）を起動。 | ・タイピング速度を一切犠牲にしない。  ・LLMの起動頻度を1/20以下に間引けるため端末負荷が低い。 | L1のルールが固すぎると、L2に届く前にユーザーが誤警告と感じるリスク。 | ◎ バランスが最も優れており、第一候補となり得る |
| パターン2: 投機的検証  (Speculative Verification) | Jevが「おそらくここはセリフ／矛盾」と投機的（仮）にフラグを立ててUIに即時反映し、裏で1B〜3BのSLMがストリーミングで検証・是正する。 | リアルタイム性と高精度な文脈判定を理論上両立できる。 | クライアント端末のVRAM/メモリ消費が常時高止まりしやすい。 | △ ローカルGPUリッチ環境（自作PC等）向けとしては有望 |
| パターン3: コンパイラ＋ランタイム型  (LLM as Semantic Parser) | 小説テキストから「Jevの特徴量ID（指し手）」への変換をLLMが担い、状態の蓄積・整合性判定はJevが行う。 | 複雑な自然言語表現を確実にスキーマへ落とし込める。 | 変換（コンパイル）にLLMを挟むため、リアルタイムの即時追従性が落ちる。 | ○ 「章ごとの一括取り込み（Ingest）」用途に極めて適している |
| パターン4: Embedding + Jev複合型  (ベクトル空間と論理空間の統合) | 意味の近さ（コサイン類似度）と、論理的制約（Jevのアキュムレータ内積）を重み付け合算してスコアリング。 | 伏線や雰囲気の整合性など、ファジーな一致度も数値化できる。 | パラメータ調整が複雑化し、なぜ警告が出たのかの因果関係が不透明になりやすい。 | △ 解釈可能性（説明責任）の面で難易度が高い |

### 3. パターン1（L1/L2 階層型）におけるオープンウェイトLLMの具体的な役割
仮にパターン1を採用した場合、オープンウェイトLLM（例: WebLLM上で動くQwen 2.5 1.5B/3B、あるいはローカルOllama経由の7B/8Bモデル）をどのように組み込むのが合理的かを検証します。

他者の独自実装やライブラリを借用せず、標準的な数学的処理（線形代数と標準的なニューラルネットワーク層）のみで構成するオリジナルモデルの概念設計です。
[本文入力の差分トークン] ──► [疎な特徴量マッパー (Feature Hashing)]                                       │ (該当IDのインデックス列: O(Δ))                                       ▼                       【自社製アキュムレータ (Narrative Accumulator)】                        - 各エンティティの状態埋め込み (128〜256次元)                        - ベクトル加算・減算のみで状態更新 (SIMD対応)                                       │                                       ▼ (結合ベクトル: 256〜512次元)                       【極小判定ヘッド (Narrative Scorer)】                        - Layer 1: Linear(512 -> 128) + GELU                        - Layer 2: Linear(128 -> 32) + GELU                        - Layer 3: Linear(32 -> 1) + Sigmoid                                       │                                       ▼                       【破綻スコア (0.0: 正常 〜 1.0: 破綻)】

### 1. オリジナル極小モデル（NarrativeEvaluator）のPyTorch定義
語彙数 V=16,384、埋め込み次元 D=128 とした場合、埋め込み層が約2.09Mパラメータ、評価ヘッドが約3.7万パラメータとなり、合計約2.13Mパラメータ（INT8量子化時に約2.1MB）に収まります。
import torchimport torch.nn as nnimport torch.nn.functional as Fclass NarrativeEvaluator(nn.Module):    """    物語状態アキュムレータとアクション特徴から破綻スコアを出力する極小モデル    総パラメータ数: 約 2.13M (Embedding: 2,097,152 + MLP: 36,993)    """    def __init__(self, vocab_size: int = 16384, embed_dim: int = 128):        super().__init__()        self.vocab_size = vocab_size        self.embed_dim = embed_dim        # 1. 疎特徴量埋め込み層 (Sparse Feature Embeddings)        # 状態およびアクションの各特徴量IDを低次元ベクトルへ投影        self.embedding = nn.Embedding(vocab_size, embed_dim, padding_idx=0)        # 2. 評価ネットワーク (Scoring MLP)        # 入力: [状態アキュムレータ(128) + アクションベクトル(128) = 256次元]        self.scorer = nn.Sequential(            nn.Linear(embed_dim * 2, 128),            nn.GELU(),            nn.Linear(128, 32),            nn.GELU(),            nn.Linear(32, 1)  # 破綻ロジットを出力        )        # 重みの初期化 (Xavier / Kaiming)        self._init_weights()    def _init_weights(self):        nn.init.normal_(self.embedding.weight, mean=0.0, std=0.02)        with torch.no_grad():            self.embedding.weight[0].fill_(0)  # padding_idxを0に固定        for m in self.scorer:            if isinstance(m, nn.Linear):                nn.init.xavier_uniform_(m.weight)                nn.init.zeros_(m.bias)    def compute_accumulator(self, state_feature_ids: torch.Tensor) -> torch.Tensor:        """        現在の物語盤面の状態特徴量群からアキュムレータを計算 (バッチ非依存)        state_feature_ids: [batch_size, num_active_features]        """        embeds = self.embedding(state_feature_ids)  # [B, N, D]        # パディングを除いた平均または総和 (ここでは平均ベクトルを採用)        mask = (state_feature_ids != 0).unsqueeze(-1).float()        sum_embeds = (embeds * mask).sum(dim=1)        count = mask.sum(dim=1).clamp(min=1.0)        return sum_embeds / count  # [B, D]    def forward(self, state_feature_ids: torch.Tensor, action_feature_ids: torch.Tensor) -> torch.Tensor:        """        通常フォワードパス（一括検証）        """        state_acc = self.compute_accumulator(state_feature_ids)      # [B, D]        action_acc = self.compute_accumulator(action_feature_ids)    # [B, D]        # 状態とアクションを結合        combined = torch.cat([state_acc, action_acc], dim=-1)        # [B, 2*D]        logits = self.scorer(combined).squeeze(-1)                   # [B]        return logits    def evaluate_incremental(self, cached_state_acc: torch.Tensor, action_feature_ids: torch.Tensor) -> torch.Tensor:        """        キーストローク時の差分高速推論パス (Wasm/オンデバイス用)        事前にキャッシュされた state_acc (128次元) と新規アクションのみを計算        """        action_acc = self.compute_accumulator(action_feature_ids)        combined = torch.cat([cached_state_acc, action_acc], dim=-1)        logits = self.scorer(combined).squeeze(-1)        return torch.sigmoid(logits)  # 0.0 (整合) 〜 1.0 (破綻)

### 3. 完全内製型：合成データ生成スクリプト（Data Generator）
外部APIに依存せず、型安全ルールの「正例（合法的展開）」と意図的な「負例（破綻注入）」を決定論的に組み上げるスクリプトの骨子です。
import randomimport numpy as npfrom typing import List, Tuple, Dictclass SyntheticNarrativeDatasetGenerator:    def __init__(self, num_samples: int = 100000, max_features: int = 16):        self.num_samples = num_samples        self.max_features = max_features        # エンティティ定義のプール        self.characters = [1, 2, 3, 4]  # アレク, エレナ, ガルド, バルク        self.items = [10, 11, 12]        # 指輪, 剣, 薬草茶        self.facts = [100, 101, 102]     # 指輪の呪い, ガルドの裏切り, 王家の血統    def _feature_id(self, category_offset: int, ent_a: int, ent_b: int) -> int:        """エンティティペアを決定論的に1つの特徴量IDへハッシュマッピング"""        return category_offset + (ent_a * 37 + ent_b) % 3500    def generate_single_case(self) -> Tuple[List[int], List[int], float]:        """        1件の物語状態・アクション・破綻ラベル(0.0 or 1.0)を生成        """        state_features = []        is_violation = random.random() < 0.5  # 50%の確率で破綻を注入        # 1. 基礎状態の構築        actor = random.choice(self.characters)        target_item = random.choice(self.items)        target_fact = random.choice(self.facts)        actor_has_item = random.choice([True, False])        actor_knows_fact = random.choice([True, False])        if actor_has_item:            # 状態: actor が target_item を所持            state_features.append(self._feature_id(1, actor, target_item))        if actor_knows_fact:            # 状態: actor が target_fact を把握            state_features.append(self._feature_id(4000, actor, target_fact))        # 2. アクションの選択（破綻判定パターンの注入）        action_type = random.choice(['USE_ITEM', 'SPEAK_SECRET'])        action_features = []        if action_type == 'USE_ITEM':            action_features.append(self._feature_id(12000, actor, target_item))            if is_violation:                # 破綻: 持っていないアイテムを使用しようとした                if actor_has_item:                    # 状態から所持特徴を削除して矛盾状態を作る                    state_features.remove(self._feature_id(1, actor, target_item))                label = 1.0            else:                # 正常: 持っているアイテムを使用                if not actor_has_item:                    state_features.append(self._feature_id(1, actor, target_item))                label = 0.0        elif action_type == 'SPEAK_SECRET':            action_features.append(self._feature_id(14000, actor, target_fact))            if is_violation:                # 破綻: 知らないはずの秘密をセリフで暴露した（主観認識違反）                if actor_knows_fact:                    state_features.remove(self._feature_id(4000, actor, target_fact))                label = 1.0            else:                # 正常: 知っている事実について発言                if not actor_knows_fact:                    state_features.append(self._feature_id(4000, actor, target_fact))                label = 0.0        # パディング処理 (長さを max_features に揃える)        state_features = (state_features + [0] * self.max_features)[:self.max_features]        action_features = (action_features + [0] * 4)[:4]        return state_features, action_features, label    def build_dataset(self) -> Dict[str, np.ndarray]:        states, actions, labels = [], [], []        for _ in range(self.num_samples):            s, a, l = self.generate_single_case()            states.append(s)            actions.append(a)            labels.append(l)        return {            'states': np.array(states, dtype=np.int64),            'actions': np.array(actions, dtype=np.int64),            'labels': np.array(labels, dtype=np.float32)        }
### 4. 学習ループとONNX（Wasm向け）エクスポート
生成されたデータを用いてモデルを収束させ、ブラウザ実行用のONNXバイナリとして書き出す基本フローです。
import torchfrom torch.utils.data import TensorDataset, DataLoaderdef train_and_export():    # 1. データの準備 (10万件生成: 数秒で完了)    generator = SyntheticNarrativeDatasetGenerator(num_samples=100000)    data = generator.build_dataset()    dataset = TensorDataset(        torch.from_numpy(data['states']),        torch.from_numpy(data['actions']),        torch.from_numpy(data['labels'])    )    dataloader = DataLoader(dataset, batch_size=256, shuffle=True)    # 2. モデルと最適化手法の初期化    device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')    model = NarrativeEvaluator().to(device)    optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3, weight_decay=1e-4)    criterion = nn.BCEWithLogitsLoss()    # 3. 学習ループ (数エポックで十分収束)    model.train()    for epoch in range(5):        total_loss = 0.0        for states, actions, labels in dataloader:            states, actions, labels = states.to(device), actions.to(device), labels.to(device)            optimizer.zero_grad()            logits = model(states, actions)            loss = criterion(logits, labels)            loss.backward()            optimizer.step()            total_loss += loss.item() * states.size(0)        print(f"Epoch {epoch+1}, Loss: {total_loss / len(dataset):.4f}")    # 4. Wasm/ONNX形式へのエクスポート (差分推論用インターフェース)    model.eval()    model.to('cpu')    # ダミー入力: 事前アキュムレータ(128次元) + アクション特徴ID(4個)    dummy_acc = torch.randn(1, 128, dtype=torch.float32)    dummy_action = torch.tensor([[12001, 0, 0, 0]], dtype=torch.int64)    # 差分実行用のラッパー    class IncrementalExportWrapper(nn.Module):        def __init__(self, base_model):            super().__init__()            self.base_model = base_model        def forward(self, cached_acc, action_ids):            return self.base_model.evaluate_incremental(cached_acc, action_ids)    export_wrapper = IncrementalExportWrapper(model)    torch.onnx.export(        export_wrapper,        (dummy_acc, dummy_action),        "narrative_evaluator_nano.onnx",        input_names=["cached_state_acc", "action_feature_ids"],        output_names=["violation_prob"],        dynamic_axes={"action_feature_ids": {0: "batch_size"}},        opset_version=17    )    print("Exported to narrative_evaluator_nano.onnx successfully.")if __name__ == '__main__':    train_and_export()
