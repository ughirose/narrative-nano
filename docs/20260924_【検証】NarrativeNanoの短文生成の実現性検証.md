- 逐次推論（Auto-regressive）に伴うレイテンシの壁解析系のEncoderは全トークンを一括（並列）でフォワードパスできますが、一文をゼロから生成するDecoderは「1トークン出力ごとに1回の推論」を繰り返す必要があります。Wasm SIMDで動作させる場合、1トークンあたり10〜30msかかったとしても、20トークンの短文で200〜600ms、環境によっては1秒を超えるケースが考えられます。これが執筆UIのリアルタイム性を損なわないかどうかが一つの論点になります。
- パラメータ数と日本語の破綻率のバランス汎用言語モデル（数B規模）と異なり、10M〜20Mクラスの極小モデルで「一文」を生成させると、助詞の重複、同一フレーズのループ、文末の不自然な終止といった崩壊が起きやすくなります。この破綻を抑えるためには、自由文生成を狙うよりも「WorldCraftの世界観構築（情景描写・キャラクターの行動・状態変化など）に特化したコーパス」で転移学習・蒸留を行い、生成タスクのドメインを意図的に狭めるアプローチが現実的かもしれません。
- scene や text からのメタ情報連携単に直前のテキストだけを入力にして次の一文を生成させる構成だと、極小モデルの文脈理解力不足が露呈しやすい傾向があります。先行する narrativenano-text や scene が抽出した「主語・述語・格関係」や「現在のシチュエーション属性（時間・天候・緊張度など）」を構造化プロンプト（制御トークン）として gen に渡すことで、パラメータ数の少なさをコンテキストの精度で補う構成が考えられます。

##### アプローチ別の検証シナリオ
- 文末の単調さ解消を先行させる場合NarrativeNanoの構文解析エンジン（text）がブラウザ上で破綻なく動くかを検証する「スモークテスト」として機能しやすいと考えられます。AIアレルギーの強い層に対しても「純粋な文法支援ツール」として提示できるため、初期の摩擦を最小化できる可能性があります。一方で、既存の校正ツールとの差別化が分かりにくく、プロダクトとしての求心力に欠けるリスクも内包しています。
- 動作描写の肉付けを先行させる場合設定辞書（キャラクター、持ち物）とシーン情報（scene）を組み合わせるため、WorldCraftの思想である「世界観設定と執筆のシームレスな統合」をダイレクトに検証できます。技術的なハードルは高くなりますが、「生成AI反対派でも納得できる、設定に即した手助け」というコアバリューを確かめるには、こちらの方がより本質的な検証になるという見方も成り立ちます。
#### 個別ユーザーの執筆癖・設定を蓄える「ローカルメモリー機能」の検証
完全ローカル・プライバシー重視のアーキテクチャにおいて、個別ユーザーの表現スタイルを蓄積する設計は、外部APIモデルにはない大きな強みになり得ます。
##### メモリーの構造とデータ層の分離案
[ ブラウザストレージ (IndexedDB / OPFS) ]  ├── 1. 静的設定メモリ (WorldCraft Entity)  │      └─ キャラクター、装備、魔法、地名（確定的な辞書）  │  ├── 2. 動的スタイルメモリ (User Stylometrics)  │      ├─ 頻出述語・語尾パターン（例：体言止めの比率、好む接続詞）  │      └─ 頻出連語（N-gram / 例：「〜を睨みつける」「〜が呟く」）  │  └── 3. コンテキストキャッシュ (Session Context)         └─ 直近のシーンで登場した単語・状態（短期的優先度付け用）

#### 2. 重み付け・スコアリングアルゴリズムの検証
執筆支援における重み付けでは、「単なる頻度」だけを採用すると過去の多用表現が固定化され、表現の幅を狭めてしまうリスク（エコチェンバー化）が懸念されます。
##### 考慮すべきスコアモデル案
候補のスコア S を算出するモデルの一例として、以下の要素を組み合わせた形式が検討対象となります。
S=直近性と採用実績(∑waction​⋅e−λΔt)​​×ユーザー特異度log(Pbase​(w)Puser​(w)​+1)​​
- 行動による重み付け (waction​)ユーザーの入力行動ごとに重みの傾斜をつけるアプローチです。
  - 高重み（+3.0〜+5.0）：サジェストされた推敲候補を明示的にクリック・採択した場合。
  - 中重み（+1.0）：自力でタイピングして確定させた場合（暗黙的嗜好）。
  - 負の重み（-1.0〜-2.0）：提示された推敲候補を無視して別の表現を選択した、あるいは直後にCtrl+Z等で取り消した場合。
- 時間減衰（半減期モデル e−λΔt）創作においては「その作品やその章だけで一時的に頻出する表現」が存在します。更新日時 Δt に応じて減衰係数をかけることで、数ヶ月前の別作品の癖が現在の文脈を過度に支配する現象を緩和できる可能性があります。
- 基本コーパスとの特異度（TF-IDF / 偏向度）一般的な日本語表現 Pbase​ に対するユーザー表現 Puser​ の比率を対数でとることで、「誰でも使う一般的な助詞・動詞」ではなく「その作家特有の言い回し（作家性）」を浮き彫りにして上位に押し上げる効果が期待されます。
#### 3. ブラウザ実行環境における技術的課題
- IndexedDBのトランザクション遅延とUIスレッドの保護キーストロークや確定ごとに直接IndexedDBへ書き込みを行うと、トランザクションのオーバーヘッドが重なり入力遅延を招く恐れがあります。
  - 二層キャッシュ構成の妥当性：直近のセッションデータはメモリ上のリングバッファまたはLRUキャッシュ（L1）に保持し、一定文字数の入力時やエディタのフォーカスアウト時にWorker経由でIndexedDB（L2）へ非同期バッチ書き込みする設計が、体感速度の維持には不可欠と見られます。
- データ容量の肥大化とプルーニング（忘却）戦略執筆が進むにつれてIndexedDBのレコード数は数万件規模に達する可能性があります。定周期（例：起動時や1万字執筆ごと）で、スコアが一定閾値を下回るレコードや、長期間更新のない低頻度エントリを破棄（Garbage Collection）するプルーニング処理を組み込まなければ、ブラウザストレージのクォータ圧迫や検索性能の劣化を招く懸念があります。

執筆癖を忠実に反映させること自体は「馴染むツール」を作る上で有用である一方、推敲の本来の目的である「表現の幅を広げる」「自身の無意識の癖を客観視して直す」という創作行為の動機と相反する側面も持ち合わせています。

#### 創作プロセスにおける非対称性の検証
- 執筆中の「思考の中断（Cognitive Load）」という観点文字を打ち込んでいる最中に「多様な言い換え」や「偏りの指摘」が頻繁に割り込むと、作業記憶（ワーキングメモリ）が散漫になり、物語の展開やキャラクターの動線から意識が逸れてしまう懸念があります。執筆の加速という観点に限れば、予測可能な手癖の再現（確定打鍵の削減）の方がノイズになりにくいと考えられます。
- 「自分の文体」の正体と自己模倣のジレンマ一方で、手癖を忠実に反映し続けると、以前書いたシーンと全く同じ構文パターン（例：「〜に目を細めた」「〜と息を吐いた」などの頻出）が無意識に再生産され、作品全体の強度が低下するという問題に直面しがちです。多くの創作者が推敲時に求めているのは「自分の癖を維持すること」ではなく、「客観的な目線で癖を発見し、意図的に崩すこと」である場合も少なくありません。
- 受容性（AI反対派・慎重派への配慮）多様化や補正を前面に出しすぎると、「作品のトーンを勝手に変えようとする他者」として認識され、ツールの受容性が下がる恐れがあります。「手癖を尊重する」スタンスを基本姿勢（デフォルト）に見せること自体が、ツールへの信頼感を醸成するための前提条件になるという見方も成り立ちます。
#### 統合的なアプローチの検討
二者択一としてどちらか一方を切り捨てるのではなく、「操作の文脈（トリガー）」によって役割を分離する設計が有効かもしれません。
[ 入力・タイピング中（インライン補完） ]   └─ 【手癖優先 (Exploitation)】        ・本人の頻出語彙、確定パターンを素早く提示し、筆を止めない[ 選択操作・推敲コマンド実行時（オンデマンド） ]   └─ 【多様化・補正優先 (Exploration)】        ・重複表現の警告や、頻度の低い類語・定型表現を提示し、幅を広げる
- 手癖を「ベースライン」、多様化を「外力」とする構成ローカルメモリーの基本機能としてはユーザーの手癖（共起パターンや語尾傾向）を忠実に学習させておき、通常サジェストではそれを優先する。一方で、同一の言い回しが短期間に集中した際（例：同一段落内で同一語尾が3回連続など）にのみ、受動的なインジケータ等で「多様化の提案」を促すような抑制的な設計が、創作者の主権を守る落としどころになる可能性があります。

#### 2. 提示枠（スロット）の配分アーキテクチャ
推敲メニュー等で複数候補（例えば3〜4枠）を提示する場合、スコア順に単純ソートすると手癖上位ばかりで埋まる、あるいは逆に突飛な候補ばかりが並ぶリスクがあります。あらかじめ「枠の役割」を固定するスロット割り当て方式が安定性をもたらす可能性があります。
[ 推敲候補ポップオーバー (4スロット構成例) ] ├─ Slot 1: 【親和枠】 ユーザー最高頻度パターン (手癖の再現) ├─ Slot 2: 【設定枠】 WorldCraft辞書・エンティティ連動 (所持品・属性等) ├─ Slot 3: 【多様化枠】 文脈適合・低使用頻度の類語 (探索的アプローチ) └─ Slot 4: 【構造変形枠】 構文変換 (体言止め、連用形接続、反転描写)
- Slot 1（親和・手癖）：本人が過去に高頻度で採択した連語・文末表現を割り当て、安心感を確保する。
- Slot 2（設定連動）：scene タグや登場人物のプロパティから拾った固有語彙を優先し、世界観のブレを防ぐ。
- Slot 3（多様化・探索）：NarrativeNanoが文脈適合度を担保しつつ、本人のローカルメモリーにおいて出現頻度が低い語彙を意図的に引き上げる。
- Slot 4（構文変形）：語彙そのものではなく、述語の活用形や品詞を機械的に組み替える（「〜だった」→「〜の姿があった」「〜と息を呑む」など）。
#### 3. 多様化スコアと手癖スコアの算出ロジック
提示順や候補選定におけるスコア付けでは、本人の頻出度と多様化要求度を動的に掛け合わせる計算式が検証対象となります。
Score(w)=(1−λ)⋅Shabit​(w)+λ⋅Sdiversity​(w)−Prepetition​(w)
- 手癖スコア Shabit​(w)：ローカルメモリー内の共起頻度や採用履歴に基づくスコア。
- 多様化スコア Sdiversity​(w)：Nanoの事前学習コーパスにおける文脈類似度が高く、かつ本人の直近執筆履歴に含まれていない度合い。
- 重複ペナルティ Prepetition​(w)：直前2〜3文、あるいは同一段落内で同一の語尾・語彙がすでに使われている場合に課される減点項。
- 動的探索率 λ（0.0 〜 1.0）：
  - 通常のインライン入力時は λ→0（手癖最大）。
  - 単調な文末が連続して検知された場合や、ユーザーが推敲メニューを開いた時は λ→0.6∼0.8（多様化重視）へシフトさせる制御が考えられます。

##### 軽量算出のアルゴリズム骨子
